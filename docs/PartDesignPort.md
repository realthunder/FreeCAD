## 3. The ledger

Generated by `scripts/port-ledger.py`:

    python scripts/port-ledger.py --base a662fbb2ff --tip 3383e9119f \
        --strip src/Mod/PartDesign/ \
        --gizmo src/Gui/Inventor/Draggers,src/Mod/Part/App/GizmoHelper \
        -o docs/PartDesignPort-ledger.tsv src/Mod/PartDesign tests/src/Mod/PartDesign

It walks `git log --no-merges --full-history` over PartDesign, its C++ tests
and the gizmo sources, and drops commits that touch only translations. The
columns are SketcherPort's, plus `family`:

- `kind`: a guess from the subject line (fix / feature / refactor / noise /
  ?), a sorting aid, not a verdict.
- `family`: `gizmo` when the commit touches the gizmo sources or its subject
  says gizmo or dragger.
- `fwd` / `rev`: whether the commit's patch, limited to the walked paths,
  `git apply --check`s forward or in reverse against the branch at creation.
- `status`: `have(rev)` (the patch reverse-applies) or `open`.
- `decision`: `taken <hash>`, `adapted <hash>`, `have`, `n/a`, `superseded`,
  `declined <why>`, `deferred`.

At creation: 800 rows (219 fix, 145 feature, 123 refactor, 75 noise, 238
unclassified), 7 `have(rev)`, 47 applying forward, 36 in the gizmo family.

Commit messages for picks: `PD: <summary> (upstream <hash>)`, or the area of
the files touched (`Gui:`, `Part:`) when that is not PartDesign.

## 4. Phase 1: the gizmo layer

What the gizmos need, and what the fork already had:

- **The dragger nodes were already here.** `f8b6a242f7` (2026-08-06) ported
  upstream's `Gui/Inventor/Draggers` -- `SoTransformDragger` and the linear,
  planar and rotation draggers with their geometry kits -- plus
  `So3DAnnotation` and `SoToggleSwitch`, for the Assembly workbench. It left
  out only the gizmo layer. The fork's copies match `3383e9119f` except for
  `SoSphereGeometry`, which the primitive gizmos (`3237a21580`) added after
  that port.
- **Taken from `3383e9119f` as files**, not replayed commit by commit, since
  none of them existed here: `Gizmo.{h,cpp}`, `GizmoStyleParameters.h`,
  `Part/App/GizmoHelper.{h,cpp}`, and `SoLinearDraggerGeometry.{h,cpp}` for the
  sphere kit. The gizmo-layer commits the files carry (`2cab5e7b64`,
  `5be668b696`, `341f352864`, `5cc05a1ab2`, `3758c20779`, `fab1b8d279`,
  `d299a787aa`, `603e0bc6e5`, `a678d8ec7f`, `d8d32c1b3a`, `d08a7f1c0d`,
  `529c624afc`) are marked taken by that commit. The PartDesign halves of
  the same commits land with their panels.
- **Adaptations:**
  - `GizmoContainer::attachViewer` takes a `Gui::ViewerContext*`, the fork's
    edit-mode seam (docs/ThinClient.md 8.3), instead of a
    `View3DInventorViewer*`, so it runs for a served mirror as it does on the
    desktop.
  - It does not reset the document's editing transform. Upstream sets it to
    the edited object's parent placement; the fork's edit path already set it
    for the object, and `ViewProviderDragger::setEditViewer` hangs the gizmos
    at the editing transform less the object's own placement, exactly as it
    hangs `csysDragger`.
  - `ViewProviderDragger` gains `setGizmoContainer()` and the attach in
    `setEditViewer`, and nothing else from upstream's rework.
  - `GizmoHelper` uses `getCenterOfGravity(Vector3d&)`; the fork has no
    `std::optional` `centerOfGravity()`.
  - The gizmo preferences (the "Experimental" group, `Gui/Gizmos`) are
    spliced into the fork's `DlgSettingsGeneral`, which has drifted too far
    from upstream's to take whole.
  - `Base::angularDist`, `Base::clampAngle` and `Vector3::Normalized()`, from
    `6e896b1248`.
- **The Pad/Pocket panel binds a gizmo to the real widget.** A gizmo drives a
  `Gui::QuantitySpinBox`. `Gizmo.cpp` stays upstream's; the panel hands it
  `FwQt::widgetOf(ui->lengthEdit)`, the same route the panel already takes
  for its other Qt-only calls, and the widget's own sync carries the value to
  the model and the property. Where there is no Qt widget there is no gizmo.
  Driving gizmos from the browser mirror is a later item.

### The panels

Each panel creates its gizmos at the end of its constructor, and re-reads
their placement in `finishedRecomputeFeature()`. Every recompute a fork
panel starts ends there, so this replaces the call sites upstream spreads
over its slots and selection handlers. The dragger hints (`6df51cefd7`)
are `TaskFeatureParameters::showDraggerHints()`; hiding them clears the
hint bar only when this panel put the hints there.

| panel | gizmos | adaptation |
|---|---|---|
| Fillet | radius, on both faces of the first edge | `getBaseShape(true)`, the fork's name for `getBaseTopoShape` |
| Chamfer | distance, second distance or angle | the type combo's index stands in for `Part::ChamferType` |
| Thickness | value, on the first face | also hidden while the feature is in error: the edge lookup throws on a dangling reference |
| Draft | angle | `FeatureDraft` keeps its last pull direction and neutral plane (`getLastComputedProps`), the App half of `6aee8b81c9` |
| Helix | height | none |
| Revolution, Groove | angle, second angle | upstream's code from before the two-sides work (`b2da06bfe0^`); it matches the fork's feature |
| Hole | depth | hole centres are the profile's circle and arc centres and the direction is the profile normal, as `Hole::execute()` has them here; no `BaseProfileType` (holes on points), no start offset |
| Box, Cylinder, Sphere | the dimensions | the Placement is watched through `slotChangedObject`; the fork's `TaskAttacher` has no `placementUpdated` signal |
| Pad, Pocket | length, second length, both tapers | Fw widgets (above); `TwoLengths` shows the second side and `Midplane` halves the step, where upstream reads `SideType`/`Type2`; no start offset |

Waiting for App features: the start-offset gizmos of Pad/Pocket and Hole
(`a01fad4f53`, and upstream's `StartType`/`StartOffset`), Revolution's two
sides (`b2da06bfe0`) and its start controls (`a4b3950ac1`). Part's own
Thickness dialog has a gizmo upstream, but upstream leaves it switched off
("a proof"), so it is not taken.

## 6. Phase 2: the fixes (2026-09-24)

### Method

The 213 open rows of kind `fix` were split App-only (96) and the rest (117),
and each half into four batches read by agents, one verdict per commit with
fork `file:line` evidence: `have`, `n/a`, `superseded`, `pick`, `adapt`,
`declined`, `depends`, `unsure`. Where a verdict rested on behaviour, the
agents ran upstream's own tests or a small script against the fork build
(the helix, loft, thickness, pocket and binder cases below were settled that
way). Every `pick` and `adapt` was then read again against the fork before it
was applied. The ledger's `decision` column carries the result: `have (...)`
and `n/a (...)` with the reason in brief, `deferred (...)` for what needs an
upstream feature the fork lacks or a fork design of its own.

Before the picks the branch had never had a complete test run; it has now:
**ctest 749/749, Python 2902 OK** (50 skipped, 6 expected failures).

### Deferred, then taken

- **The helix family**, `161a2cb92f`. The fork swept a helix with
  MakePipeShell, a conical one with an auxiliary spine that turns the
  profile out of the meridian plane. Upstream's testCone has a profile that
  touches itself turn to turn, so its exact volume is
  A * 2 pi turns * r_mid = 500 * 13.823 * 56.18 = 3.8829e5; the fork gave
  3.7757e5, and giant helices came out invalid. Upstream's sweep (MakePipe,
  Frenet, the path broken per turn only for a cylindrical helix, its start
  offset rule, `Tolerance`) is a second path gated on
  `_ProfileBasedVersion`: 3 for a new helix, and 0 -- an upstream file --
  takes it too; 1 and 2, the fork's own, keep the old sweep and their
  element names. Names come from `makEShape()` over the MakePipe; a fillet
  on a cap edge survives a pitch change. `makeSpiralHelix()` takes the
  approximation tolerance as an argument, so `7680872e41`'s scaled
  tolerance reaches the PD helix only. `39c902c616`'s unconditional
  ShapeFix_Solid is declined: it drops the element map. TestHelix.py, which
  the fork never had, is taken whole (9 tests, 12 s where the old sweep
  took 106 s); one tolerance in it is raised for OCCT 8.0.1, see the
  commit. New behaviour: a subtractive helix with no base is an error.
- **Suppress and a cut that removes nothing**, `9262292976`. Both were
  real: a free-placed box, suppressed and unsuppressed, came back at the
  base's origin (the body lost it, 1056 -> 1000 mm^3); a subtractive box
  missing the base put the body at the cutter. One cause:
  `Part::Feature::onChanged(Shape)` equates a shape's own location with
  Placement, and both paths set a shape carrying a location of its own.
  `wrapLocated()` puts such a shape in a compound. Tests in TestPrimitive.

- **Relinking after a feature is removed**, `12f05938b7`. Worse here than
  upstream's report: the dress-up's Base follows BaseFeature carrying the
  removed feature's mapped names, so even an edge with the right index
  failed ("Invalid edge link: Edge3"). `onBaseFeatureRerouted()` runs
  before the reroute, resolves each name in the removed feature's shape and
  searches the new base by geometry; all-or-nothing, as upstream. Dress-up
  Base, and Profile and UpToFace of a profile-based feature. Two tests in
  TestFillet.
- **Pattern panels record on OK**, `bd3c94f9a8`; the sub-task of a
  MultiTransform records on its own OK, not in `closeSubTask()`, which also
  runs after a Cancel. Driven in the GUI (below).
- **An empty Fillet/Chamfer**, `bc1e3e016f`: recomputes only itself, so
  the unavoidable error is not reported before the panel opens.
